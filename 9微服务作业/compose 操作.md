在经历了前面配置 MySQL、RabbitMQ 和各种排错的实战后，你其实已经接触到了 Docker Compose 最核心的操作！

`docker-compose.yml` 文件本质上就是一份“基础设施施工图纸”。而 `docker compose` 系列命令，就是你指挥系统按照图纸施工、拆除或维修的对讲机。

为了方便你日常开发查阅，我为你整理了一份**进阶版的 Docker Compose 核心操作指南**。

### 📍 核心前提：你必须“站在图纸旁边”

在执行绝大多数操作前，你必须通过 `cd` 命令进入到包含 `docker-compose.yml` 文件的那个文件夹（比如你的 `~/env-workspace`）。否则，Docker 就会向你抱怨 `no configuration file provided: not found`。

### 🛠️ 1. 日常开发：生命周期管理（全家桶操作）

当你需要对整个环境（比如你那 5 个中间件）进行统一步调的控制时，使用这些基础命令：

|**你的需求**|**终端命令**|**背后发生的事情**|
|---|---|---|
|**一键启动所有服务**| `docker compose up -d` |按照图纸创建并启动所有容器。`-d` 代表在后台默默运行，不霸占你的终端控制权。|
|**下班关机 (保留数据)**| `docker compose stop` |温和地暂停所有服务。容器还在硬盘上睡大觉，明天敲 `start` 能瞬间唤醒。|
|**上班开机 (极速唤醒)**| `docker compose start` |极速唤醒昨晚 `stop` 的容器，不需要重新解析图纸。|
|**遇到卡顿，重启环境**| `docker compose restart` |相当于按了主机的重启键，所有服务依次关闭再开启。|
|**彻底销毁 (危险操作)**| `docker compose down` |**拆毁整栋楼**。容器和网络会被彻底删掉，但不用慌，挂载到你本地 `./data` 的核心数据依然存活。|

### 🎯 2. 精准打击：单点故障排查与控制

在微服务开发中，最常用的往往不是全量操作，而是像你刚才修复 RabbitMQ 那样，**只针对某一个“出头鸟”进行操作**。

> **提示：** 下面的 `[服务名]` 指的是你在 yaml 文件里写的顶级节点名字，比如 `mysql`、`rabbitmq`，**不是**长长的容器名 `dev-rabbitmq`。

|**你的需求**|**终端命令**|**适用场景**|
|---|---|---|
|**查看大家都活得好吗**| `docker compose ps` |查看所有容器的运行状态和映射端口。如果看到谁是 `Exited`，说明它挂了。|
|**抓内鬼：看实时报错**| `docker compose logs -f [服务名]` |**排错神器**！比如刚才查 `Too short cookie string` 就是靠它。`-f` 会让日志像流水一样实时刷新，按 `Ctrl+C` 退出。|
|**只重启某个坏掉的服务**| `docker compose restart [服务名]` |比如只有 Nacos 卡了，那就只重启 `nacos`，数据库和缓存不受影响。|
|**修改配置后，单独更新**| `docker compose up -d [服务名]` |如果你只修改了 `docker-compose.yml` 里 Redis 的密码，敲这个命令，Docker 会**聪明地只重建 Redis**，其他服务原封不动。|
|**彻底挫骨扬灰 (终极重置)**| `docker compose rm -s -v -f [服务名]` |当某个容器陷入死循环、彻底坏掉时使用。强行停止、删除并解除它的匿名数据卷绑定。|

### 📝 3. 编写 `docker-compose.yml` 的黄金法则

在维护和修改这份“图纸”时，遵循这些原则能让你少踩很多坑：

- **空格是神圣的（YAML 语法）**：千万不要用 `Tab` 键缩进，严格使用空格（通常是两个空格为一层）。同层级的配置项必须绝对对齐，错位一个空格就会报错。
    
- **服务依赖 (`depends_on`)**：如果在微服务里，业务 A 强依赖数据库 B，一定要在 A 下面写 `depends_on: b`。加上 `condition: service_healthy` 更是能完美解决启动时序问题。
    
- **密码分离 (`.env`)**：永远不要把生产环境的密码明文写在 `.yml` 里，使用我们之前配置的 `${DEV_PASSWORD}` 加 `.env` 文件的组合，既安全又方便一键改密。
