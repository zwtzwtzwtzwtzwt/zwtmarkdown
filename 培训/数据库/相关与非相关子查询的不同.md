# 相关和非相关的不同  
### 核心本质区别

两者最根本的差异只有一条：**子查询是否引用外层查询的字段、能否脱离外层独立运行**。 所有执行逻辑、执行次数、性能特性的区别，都由这一点衍生而来。

- 非相关子查询：完全独立，自己就能跑通
- 相关子查询：依赖外层字段，单独运行会报「未知列」错误

---

### 一、完整差异对比表

|对比维度|非相关子查询|相关子查询|
|---|---|---|
|**核心定义**|子查询内部**不引用任何外层表的字段**，逻辑完全独立|子查询的条件/计算中**引用了外层表的字段**，必须依赖外层传入值|
|**可独立运行**|单独复制子查询代码，可正常执行并返回完整结果|单独运行会报错（提示字段不存在），必须嵌套在外层中才能执行|
|**执行次数**|整条 SQL 中**只执行 1 次**，生成固定结果后全局复用|外层每遍历 1 行数据，子查询就执行 1 次，执行次数≈外层表行数|
|**执行时机**|所在子句阶段启动时，一次性执行完毕（比如 WHERE 阶段开头）|外层处理到当前行、需要用到子查询结果时，才触发执行|
|**结果特性**|返回**全局统一的固定结果集/值**，所有外层行共用同一份结果|返回**随当前行动态变化的结果**，每行对应不同的计算/判断结果|
|**典型写法**| `WHERE 字段 IN (子查询)`、`FROM (子查询) 别名`、固定聚合标量子查询| `WHERE EXISTS (子查询)`、`SELECT 列表里的关联子查询`、带外层字段的行级比较|
|**优化器处理**|大概率被改写为**半连接/表连接**，消除子查询结构|多数保留嵌套执行逻辑，部分简单场景可被优化为连接|

---

### 二、非相关子查询详解

#### 核心特征

子查询是一个“自给自足”的独立查询，和外层表没有任何数据依赖，相当于一个固定的“结果容器”，先算好再给外层用。

#### 常见示例

1. **WHERE 后的 IN 子查询（最典型）**

```
SELECT * FROM emp 
WHERE dept_id IN (SELECT id FROM dept WHERE name = '研发部');
```

子查询 `SELECT id FROM dept ...` 完全不依赖外层 `emp` 表的任何字段，单独复制出来可以正常运行。 执行时先一次性拿到所有研发部的 ID，再用这个固定集合过滤员工表。

2. **FROM 后的派生表**

```
SELECT t.dept_id, t.avg_sal 
FROM (SELECT dept_id, AVG(sal) avg_sal FROM emp GROUP BY dept_id) t 
WHERE t.avg_sal > 5000;
```

括号里的分组聚合子查询完全独立，先执行生成临时表 `t`，再参与外层的过滤。

3. **SELECT 中的固定标量子查询**

```
SELECT name, sal, (SELECT MAX(sal) FROM emp) AS max_sal 
FROM emp;
```

子查询返回全公司最高工资，是一个固定值，和当前行员工无关，所有行共用同一个结果。

---

### 三、相关子查询详解

#### 核心特征

子查询的逻辑里“嵌入”了外层表的字段，它的计算条件由外层当前行的数据决定，只能跟着外层逐行运行。

#### 常见示例

1. **WHERE 后的 EXISTS 子查询（最典型）**

```
SELECT * FROM emp e 
WHERE EXISTS (SELECT 1 FROM dept d WHERE d.id = e.dept_id AND d.name = '研发部');
```

子查询里用到了外层的 `e.dept_id`，单独运行会报错 `Unknown column 'e.dept_id'`。 执行时遍历员工表，每取一行员工，就把它的部门 ID 传进子查询，判断是否存在匹配的部门。

2. **SELECT 列表中的关联标量子查询**

```
SELECT 
  e.name,
  (SELECT d.name FROM dept d WHERE d.id = e.dept_id) AS dept_name
FROM emp e;
```

每一行员工的部门 ID 不同，子查询返回的部门名也不同，必须逐行计算。

3. **带行级动态比较的 WHERE 子查询**

```
SELECT * FROM emp e 
WHERE sal > (SELECT AVG(sal) FROM emp WHERE dept_id = e.dept_id);
```

查询“工资高于本部门平均工资的员工”，子查询的平均值由当前员工的部门决定，每行的计算基准都不一样。

---

### 四、1 秒快速判断方法

把括号里的子查询完整复制出来，单独执行：

- ✅ 能正常运行、返回结果 → **非相关子查询**
- ❌ 报错「未知列/字段不存在」 → **相关子查询**

---

### 五、常见误区补充

1. **不是写在 WHERE 里的都是相关子查询** `WHERE IN (子查询)` 是标准的非相关子查询，只有子查询里出现了外层表的别名和字段，才是相关子查询。
2. **相关子查询≠性能差** 当外层表行数少、子查询表的关联字段有索引时，相关子查询“找到即停”的嵌套循环逻辑，反而比“先生成全量结果集”的非相关子查询更快。
3. **边界会被优化器打破** 很多写法上的非相关子查询，最终执行时会被 MySQL 优化器改写成表连接，不再以子查询的逻辑运行；部分简单的相关子查询也会被优化为半连接，执行效率大幅提升。

# in 和 exist
### 核心结论

`IN` 本质是**集合包含匹配**，基于子查询返回的完整结果集做批量比对；`EXISTS` 本质是**存在性校验**，基于外层逐行传入的值做单次存在判断。二者语义近似但执行机制、NULL 处理、性能适用场景差异很大，其中 `NOT IN` 和 `NOT EXISTS` 的语义差别是 SQL 最经典的坑之一。

---

### 一、核心执行逻辑对比

我们用同一场景的两种写法来拆解执行流程：

```
-- IN 写法
SELECT * FROM emp WHERE dept_id IN (SELECT id FROM dept WHERE name = '研发部');

-- EXISTS 写法
SELECT * FROM emp e WHERE EXISTS (SELECT 1 FROM dept d WHERE d.id = e.dept_id AND d.name = '研发部');
```

#### 1. IN 的执行流程（集合匹配）

1. **先执行子查询**：一次性执行完括号内的 SQL，得到「研发部所有部门 ID」的静态结果集合；
2. **外层逐行匹配**：遍历员工表每一行，拿当前行的 `dept_id` 去集合里做比对，存在则保留该行。
    
    > 特点：子查询只执行 1 次，生成固定集合，外层和集合做批量匹配，属于**非相关子查询**的典型用法。
    

#### 2. EXISTS 的执行流程（存在校验）

1. **先遍历外层表**：取出员工表的第一行数据，把该行的 `e.dept_id` 传入子查询；
2. **子查询做存在判断**：在部门表中查找是否存在满足条件的行，**找到第一行就立刻返回 true，停止继续扫描**；如果找不到就返回 false；
3. 根据返回的布尔值决定是否保留当前员工行，重复上述过程遍历所有员工。
    
    > 特点：子查询执行次数≈外层表行数，每次只做“有没有”的判断，不返回完整数据，属于**相关子查询**的典型用法。
    

---

### 二、核心差异对照表

| 对比维度        | IN                               | EXISTS                                    |
| ----------- | -------------------------------- | ----------------------------------------- |
| **核心语义**    | 判断外层字段值是否**包含在**子查询结果集中          | 判断子查询中是否**存在**至少一行满足关联条件                  |
| **子查询类型**   | 通常为**非相关子查询**，不依赖外层字段            | 必须是**相关子查询**，依赖外层传入的字段值                   |
| **执行次数**    | 子查询仅执行 **1 次**，生成完整结果集           | 子查询执行 **N 次**（N≈外层表行数），逐行触发               |
| **匹配逻辑**    | 全量结果集逐一比对，值相等则匹配                 | 找到第一条符合条件的行就终止，返回布尔值                      |
| **返回值要求**   | 子查询必须且只能返回 **1 个字段**（多列会报错）      | 子查询返回任意列都可以，只看有没有行，不看内容                   |
| **终止条件**    | 子查询必须跑完所有行才能得到完整集合               | 子查询找到第一行匹配数据就立即返回                         |
| **NULL 处理** | 匹配 NULL 时结果为 UNKNOWN，NULL 行不会被选中 | 只判断结果集是否为空，与返回值无关，`SELECT NULL` 也会返回 true |

---

### 三、性能对比与适用场景

没有绝对的谁更快，取决于两张表的数据量、索引情况，以及 MySQL 优化器的改写策略。

#### 1. 子查询结果集小 → IN 更优

当子查询筛选后结果集很小（比如几个、几十个 ID），IN 生成的小集合可以通过哈希匹配快速完成外层比对，整体开销低于逐行循环的 EXISTS。

> 典型场景：子查询是小表、筛选条件很严格，返回结果极少。

#### 2. 子查询表数据量大、关联字段有索引 → EXISTS 更优

当子查询表数据量极大，但关联字段（比如 `dept.id`）有主键/唯一索引时，EXISTS 每次只需要走索引查找一次，找到就停，不需要扫描全表生成完整结果集。 此时 IN 需要先生成大结果集，再做批量匹配，开销反而更高。

> 典型场景：子查询是大表、关联字段有索引，外层表行数相对较少。

#### 3. 补充：MySQL 优化器的改写

在 MySQL 5.6 及以上版本中，优化器会自动对大多数 `IN` 子查询做**半连接（Semi-Join）优化**，改写后的执行计划和 EXISTS 基本一致，性能差别很小。 但对于多层嵌套、带聚合的复杂子查询，优化器可能无法改写，此时二者性能差异会比较明显。

---

### 四、最容易踩坑：NULL 值处理

这是 IN 和 EXISTS 最大的语义差别，尤其是 `NOT IN` 和 `NOT EXISTS`，稍有不慎就会得到错误结果。

#### 1. 普通 IN / EXISTS 与 NULL

- **IN 遇到 NULL**：`dept_id IN (1, 2, NULL)` 等价于 `dept_id=1 OR dept_id=2 OR dept_id=NULL`。由于 `NULL = 任何值` 结果都是 UNKNOWN，所以外层 NULL 行不会被选中，集合里的 NULL 也不会匹配到任何行。
- **EXISTS 遇到 NULL**：只判断结果集是否存在，和返回的数值无关。`WHERE EXISTS (SELECT NULL)` 会返回所有外层行，因为子查询总能返回一行数据，哪怕值是 NULL。

#### 2. 大坑：NOT IN 与 NOT EXISTS

这是 SQL 最经典的坑之一，二者语义完全不同：

- **NOT IN**：`dept_id NOT IN (1, 2, NULL)` 等价于 `dept_id!=1 AND dept_id!=2 AND dept_id!=NULL`。 由于 `dept_id!=NULL` 永远是 UNKNOWN，整个表达式结果为假，**最终查询结果会返回 0 行**，哪怕有大量符合条件的数据。
    
    > 只要子查询返回的结果里包含一个 NULL，NOT IN 就会全军覆没。
    
- **NOT EXISTS**：仍然是“子查询找不到匹配行就返回 true”，NULL 只会导致单条不匹配，不会影响整体结果，语义稳定。

示例对比：

```
-- 若 dept 表的 id 存在 NULL 值，结果为空！
SELECT * FROM emp WHERE dept_id NOT IN (SELECT id FROM dept);

-- 无论 dept 表有没有 NULL，结果都符合预期
SELECT * FROM emp e WHERE NOT EXISTS (SELECT 1 FROM dept d WHERE d.id = e.dept_id);
```

---

### 五、选型总结

1. 简单集合匹配、子查询结果集小：优先用 `IN`，写法直观简洁；
2. 子查询是大表、关联字段有索引：优先用 `EXISTS`，利用“找到即停”的特性提升性能；
3. 涉及 `NOT` 取反的场景：优先用 `NOT EXISTS`，避免 NULL 导致的结果为空的坑；
4. 绝大多数业务场景下，二者写法可以等价改写，现代 MySQL 中性能差异不大。

# 对 null 的处理  



> 场景：**内层子查询的数据里存在 NULL**（比如 sc 表有一行 sid = NULL）

1. ✅ `NOT IN`：**直接返回 0 行，一条都没有**（这个你理解对了）
2. ❌ `NOT EXISTS` **不会把 NULL 显示在结果里**！`NOT EXISTS` 正常返回符合条件的学生记录，**NULL 不会出现在最终查询结果的行中**。

---

## 用刚才那个小案例演示

student 表：

|sid|sname|
|---|---|
|1|张三|
|2|李四|
|3|王五|

sc 表（有一行 sid 是 NULL）：

|sid|cid|
|---|---|
|1|10|
|NULL|10|

需求：找出**没有选 cid=10 课程**的学生。

### 写法 1：NOT IN

```
SELECT sid, sname FROM student
WHERE sid NOT IN (SELECT sid FROM sc WHERE cid=10);
```

内层子查询返回集合：`(1, NULL)` `sid NOT IN (1, NULL)` → 全部表达式都是 UNKNOWN，WHERE 不保留 UNKNOWN 👉 **输出：0 行，什么都不返回**

### 写法 2：NOT EXISTS

```
SELECT s.sid, s.sname FROM student s
WHERE NOT EXISTS (
    SELECT 1 FROM sc
    WHERE sc.sid = s.sid AND cid=10
);
```

逐行判断外层学生：

- s.sid=1：sc 存在 sid=1 的记录 → EXISTS=true → NOT EXISTS=false，不返回
- s.sid=2：sc 找不到 sid=2 的记录 → EXISTS=false → NOT EXISTS=true，返回 `2,李四`
- s.sid=3：sc 找不到 sid=3 的记录 → EXISTS=false → NOT EXISTS=true，返回 `3,王五`

> sc 里那行 `sid=NULL` 的选课记录：`NULL = 2` 的结果是 UNKNOWN，不会匹配上任何外层学生。 ✅ **最终结果：两行 (2,李四)、(3,王五)，结果里完全没有 NULL！**

---

## 你刚才那句话的误区在哪？

> “exist 会正常返回但是 null 的部分显示 null”

❌ 错误理解：NOT EXISTS 会把内层的 NULL 带到结果里。 ✅ 真相： `NOT EXISTS` 只判断**有没有匹配的行**。内层的 NULL 记录，仅仅是**无法匹配到任何外层学生**，它不会被当成结果输出。 最终 select 的是外层 student 表的 `s.sid, s.sname`，student 表本身没有 NULL，输出自然不会出现 NULL。

---

## 额外补充：什么时候结果里会出现 NULL？

只有 **LEFT JOIN + IS NULL** 的写法，临时连接字段才会出现 NULL：

```
SELECT DISTINCT s.sid, s.sname
FROM student s
LEFT JOIN (SELECT sid FROM sc WHERE cid=10) temp
ON s.sid = temp.sid
WHERE temp.sid IS NULL;
```

左连接的时候：

- 学生 2、3，没有匹配到 temp 表，`temp.sid` 填充为 NULL。
- 然后 WHERE 筛选 `temp.sid IS NULL`，取出这两行。
    
    > ⚠️ 这里的 NULL 是**连接产生的临时字段 temp.sid**，不是我们 select 输出的 `s.sid`，输出的学生 sid 仍然是正常数字！
    

---

## 一句话浓缩

1. NOT IN：子查询集合包含 NULL → **直接 0 行**
2. NOT EXISTS：内层有 NULL 不影响，**正常返回符合条件行，结果不会多出 NULL**
3. LEFT JOIN：中间临时表会产生 NULL（用来筛选），但最终 select 的学生字段本身还是正常值。
