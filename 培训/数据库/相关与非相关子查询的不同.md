


### 核心结论

`IN` 本质是**集合包含匹配**，基于子查询返回的完整结果集做批量比对；`EXISTS` 本质是**存在性校验**，基于外层逐行传入的值做单次存在判断。二者语义近似但执行机制、NULL 处理、性能适用场景差异很大，其中 `NOT IN` 和 `NOT EXISTS` 的语义差别是 SQL 最经典的坑之一。

---

### 一、核心执行逻辑对比

我们用同一场景的两种写法来拆解执行流程：

```
-- IN 写法
SELECT * FROM emp WHERE dept_id IN (SELECT id FROM dept WHERE name = '研发部');

-- EXISTS 写法
SELECT * FROM emp e WHERE EXISTS (SELECT 1 FROM dept d WHERE d.id = e.dept_id AND d.name = '研发部');
```

#### 1. IN 的执行流程（集合匹配）

1. **先执行子查询**：一次性执行完括号内的 SQL，得到「研发部所有部门 ID」的静态结果集合；
2. **外层逐行匹配**：遍历员工表每一行，拿当前行的 `dept_id` 去集合里做比对，存在则保留该行。
    
    > 特点：子查询只执行 1 次，生成固定集合，外层和集合做批量匹配，属于**非相关子查询**的典型用法。
    

#### 2. EXISTS 的执行流程（存在校验）

1. **先遍历外层表**：取出员工表的第一行数据，把该行的 `e.dept_id` 传入子查询；
2. **子查询做存在判断**：在部门表中查找是否存在满足条件的行，**找到第一行就立刻返回 true，停止继续扫描**；如果找不到就返回 false；
3. 根据返回的布尔值决定是否保留当前员工行，重复上述过程遍历所有员工。
    
    > 特点：子查询执行次数≈外层表行数，每次只做“有没有”的判断，不返回完整数据，属于**相关子查询**的典型用法。
    

---

### 二、核心差异对照表

|对比维度|IN|EXISTS|
|---|---|---|
|**核心语义**|判断外层字段值是否**包含在**子查询结果集中|判断子查询中是否**存在**至少一行满足关联条件|
|**子查询类型**|通常为**非相关子查询**，不依赖外层字段|必须是**相关子查询**，依赖外层传入的字段值|
|**执行次数**|子查询仅执行 **1 次**，生成完整结果集|子查询执行 **N 次**（N≈外层表行数），逐行触发|
|**匹配逻辑**|全量结果集逐一比对，值相等则匹配|找到第一条符合条件的行就终止，返回布尔值|
|**返回值要求**|子查询必须且只能返回 **1 个字段**（多列会报错）|子查询返回任意列都可以，只看有没有行，不看内容|
|**终止条件**|子查询必须跑完所有行才能得到完整集合|子查询找到第一行匹配数据就立即返回|
|**NULL 处理**|匹配 NULL 时结果为 UNKNOWN，NULL 行不会被选中|只判断结果集是否为空，与返回值无关，`SELECT NULL` 也会返回 true|

### 三、性能对比与适用场景

没有绝对的谁更快，取决于两张表的数据量、索引情况，以及 MySQL 优化器的改写策略。

#### 1. 子查询结果集小 → IN 更优

当子查询筛选后结果集很小（比如几个、几十个 ID），IN 生成的小集合可以通过哈希匹配快速完成外层比对，整体开销低于逐行循环的 EXISTS。

> 典型场景：子查询是小表、筛选条件很严格，返回结果极少。

#### 2. 子查询表数据量大、关联字段有索引 → EXISTS 更优

当子查询表数据量极大，但关联字段（比如 `dept.id`）有主键/唯一索引时，EXISTS 每次只需要走索引查找一次，找到就停，不需要扫描全表生成完整结果集。 此时 IN 需要先生成大结果集，再做批量匹配，开销反而更高。

> 典型场景：子查询是大表、关联字段有索引，外层表行数相对较少。

#### 3. 补充：MySQL 优化器的改写

在 MySQL 5.6 及以上版本中，优化器会自动对大多数 `IN` 子查询做**半连接（Semi-Join）优化**，改写后的执行计划和 EXISTS 基本一致，性能差别很小。 但对于多层嵌套、带聚合的复杂子查询，优化器可能无法改写，此时二者性能差异会比较明显。

### 四、最容易踩坑：NULL 值处理

这是 IN 和 EXISTS 最大的语义差别，尤其是 `NOT IN` 和 `NOT EXISTS`，稍有不慎就会得到错误结果。

#### 1. 普通 IN / EXISTS 与 NULL

- **IN 遇到 NULL**：`dept_id IN (1, 2, NULL)` 等价于 `dept_id=1 OR dept_id=2 OR dept_id=NULL`。由于 `NULL = 任何值` 结果都是 UNKNOWN，所以外层 NULL 行不会被选中，集合里的 NULL 也不会匹配到任何行。
- **EXISTS 遇到 NULL**：只判断结果集是否存在，和返回的数值无关。`WHERE EXISTS (SELECT NULL)` 会返回所有外层行，因为子查询总能返回一行数据，哪怕值是 NULL。

#### 2. 大坑：NOT IN 与 NOT EXISTS

这是 SQL 最经典的坑之一，二者语义完全不同：

- **NOT IN**：`dept_id NOT IN (1, 2, NULL)` 等价于 `dept_id!=1 AND dept_id!=2 AND dept_id!=NULL`。 由于 `dept_id!=NULL` 永远是 UNKNOWN，整个表达式结果为假，**最终查询结果会返回 0 行**，哪怕有大量符合条件的数据。
    
    > 只要子查询返回的结果里包含一个 NULL，NOT IN 就会全军覆没。
    
- **NOT EXISTS**：仍然是“子查询找不到匹配行就返回 true”，NULL 只会导致单条不匹配，不会影响整体结果，语义稳定。

示例对比：

```
-- 若 dept 表的 id 存在 NULL 值，结果为空！
SELECT * FROM emp WHERE dept_id NOT IN (SELECT id FROM dept);

-- 无论 dept 表有没有 NULL，结果都符合预期
SELECT * FROM emp e WHERE NOT EXISTS (SELECT 1 FROM dept d WHERE d.id = e.dept_id);
```

---

### 五、选型总结

1. 简单集合匹配、子查询结果集小：优先用 `IN`，写法直观简洁；
2. 子查询是大表、关联字段有索引：优先用 `EXISTS`，利用“找到即停”的特性提升性能；
3. 涉及 `NOT` 取反的场景：优先用 `NOT EXISTS`，避免 NULL 导致的结果为空的坑；
4. 绝大多数业务场景下，二者写法可以等价改写，现代 MySQL 中性能差异不大。
