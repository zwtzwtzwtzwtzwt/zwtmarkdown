# 子查询的执行时机
核心结论先给你：**MySQL 既不是“看到子查询就一律先执行”，也不是完全“走到哪查到哪”**。真实流程是：先做解析优化判断子查询类型，再按「子查询所在的执行阶段 + 是否依赖外层数据」来决定具体执行时机，整体服从 SQL 的标准执行链路。

下面拆开讲清楚整个过程：

---

### 第一步：执行前先做解析与优化，很多子查询会被“消灭”

在真正开始执行数据读取之前，MySQL 的优化器会先对整条 SQL 做语法解析、语义检查和查询重写。这一步会先识别出所有子查询，然后判断能不能改写优化：

- 如果是**可优化的非相关子查询**（比如 `WHERE IN (子查询)`），优化器很可能直接把它改写成**半连接（Semi-Join）**，和普通的表连接走一样的执行逻辑。 这种情况下，原本的“子查询”会消失，变成两张表的关联执行，也就不存在“先执行子查询”这个说法了。
- 如果是**无法改写的子查询**（比如部分相关子查询、聚合子查询），优化器才会保留子查询结构，进入执行阶段再按规则执行。

简单说：**不是有子查询就按子查询执行，优化器先想办法把它变成更高效的连接**。  
> 我用**同一个例子+前后对比**的方式给你讲透，你就能明白“优化器改写子查询”到底在做什么，以及为什么改写后就不存在“先执行子查询”了。
> 
> ---
> 
> ### 一句话通俗总结
> 
> MySQL 优化器就像一个“老司机”，看到你写了 `WHERE IN (子查询)` 这种两层嵌套的写法，不会傻乎乎地严格按“先跑里面、再跑外面”去执行。它会先琢磨：**能不能把这两层嵌套，等价改成两张表直接关联的写法？** 能改的话，它就会在真正执行数据前，把 SQL 的逻辑从“子查询模式”重写成“表连接模式”。改完之后，执行的时候就没有“内层子查询”这个独立步骤了，自然也就谈不上“谁先执行”。
> 
> ---
> 
> ### 第一步：先看「没改写时，IN 子查询原本怎么跑」
> 
> 我们还用这个经典例子：
> 
> ```
> SELECT * FROM emp 
> WHERE dept_id IN (SELECT id FROM dept WHERE name = '研发部');
> ```
> 
> 如果优化器不做任何改写，严格按子查询逻辑执行，流程是**严格的两步走，有明确先后顺序**：
> 
> 1. **第一步：先完整执行子查询** 先跑到 `dept` 表里，把所有 `name='研发部'` 的 `id` 全部查出来，比如得到结果 `[10, 20, 30]`，存成一个临时的固定集合。 这一步必须全部跑完，拿到完整的部门ID列表，才能进入下一步。
> 2. **第二步：再执行外层查询** 遍历 `emp` 员工表的每一行，拿当前行的 `dept_id` 去刚才的 `[10,20,30]` 集合里比对，在里面就保留，不在就丢弃。
> 
> > 这就是你之前理解的“先执行子查询”——它是两个独立的步骤，里层完全跑完，外层才开始。
> 
> ---
> 
> ### 第二步：优化器改写后，「半连接」是怎么跑的
> 
> 优化器会判断：这条 SQL 的逻辑，本质上就是“找出有对应研发部门的员工”，和“两张表按部门ID关联”的语义是一样的。 于是它会在**不改变最终结果**的前提下，把 SQL 逻辑重写成**半连接（Semi-Join）** 模式：
> 
> ```
> 逻辑等价改写为：
> SELECT emp.* 
> FROM emp 
> SEMI JOIN dept ON emp.dept_id = dept.id 
> WHERE dept.name = '研发部'
> ```
> 
> 注意：`SEMI JOIN` 不是 SQL 语法关键字，是 MySQL 内部的执行逻辑，用户看不到这个写法。
> 
> #### 改写之后的执行变化
> 
> 1. **不再有“内层子查询”这个独立步骤** 原来的“子查询结果集”消失了，变成了 `emp` 和 `dept` 两张表直接做关联。执行的时候是一个整体的关联操作，而不是分开的两步。
> 2. **执行顺序不再固定“先里后外”** 优化器可以自由选择哪张表先跑：
>     
>     - 方案A：先过滤 `dept` 表得到研发部，再去关联 `emp` 表（和原顺序类似）
>     - 方案B：先遍历 `emp` 表，每一行去 `dept` 表的索引上查有没有匹配的研发部（和 `EXISTS` 的逻辑一模一样）
>     
>     具体选哪种，由优化器根据两张表的数据量、索引情况来决定，**不再是必须先执行原来的“子查询部分”**。
> 
> ---
> 
> ### 关键补充：半连接 ≠ 普通的 INNER JOIN
> 
> 很多人会以为“就是改成 INNER JOIN 嘛”，其实不对，这是两个概念：
> 
> - **普通 INNER JOIN**：右表有多少行匹配，左表就会返回多少行。如果 `dept` 表有2个研发部记录，那一个员工可能会被返回2次，结果会重复。
> - **半连接（Semi-Join）**：只判断“右表有没有匹配”，只要存在匹配，左表的行**只返回1次**，不会重复。它的语义和 `IN`、`EXISTS` 完全一致。
> 
> 优化器用半连接，既享受到了表连接的性能优势，又保证结果和你写的子查询完全一样。
> 
> ---
> 
> ### 优化器为什么非要做这件事？
> 
> 核心是**性能**。原来的子查询两步走有明显短板：
> 
> 1. 如果子查询结果很大（比如几万个ID），生成临时集合、存内存、再逐行比对的开销很高；
> 2. 固定“先子后外”的顺序很死板，有时候反过来跑（先外层再内层）会更快，但子查询模式做不到。
> 
> 改成表连接之后：
> 
> - 可以利用关联字段上的索引，快速匹配；
> - 可以灵活选择驱动表（小表驱动大表）；
> - 可以用哈希连接、嵌套循环连接等更成熟的优化算法。
> 
> 简单说：同样的结果，用连接跑比用子查询跑，大概率更快。
> 
> ---
> 
> ### 哪些子查询会被改写？哪些不会？
> 
> 对应你最开始引用的那段话：
> 
> #### 1. 会被改写的：可优化的非相关子查询
> 
> 最典型的就是 `WHERE 字段 IN (非相关子查询)`。
> 
> - 子查询不依赖外层的任何字段，可以独立运行；
> - 逻辑上能等价转换成半连接，结果完全一致。
> 
> #### 2. 不会被改写的：无法等价成连接的子查询
> 
> - **相关子查询**：比如 `EXISTS` 里引用了外层字段，本身就已经是逐行关联的逻辑了，不需要再改；
> - **带聚合/分组的子查询**：比如 `FROM` 后面的派生表、`IN` 里套了 `GROUP BY`，结构复杂，没法直接改成简单连接；
> - **部分 NOT IN / 多层嵌套**：语义特殊或结构太复杂，优化器判断改写风险高，就会保留原结构。
> 
> ---
> 
> ### 最终总结
> 
> 你原文里的“不是有子查询就按子查询执行，优化器先想办法把它变成更高效的连接”，翻译成人话就是：
> 
> > 你写的是子查询的样子，但 MySQL 不一定按子查询的逻辑去跑。它会先检查一遍，能改成更高效的表连接就改；改不了的，才老老实实按子查询的规则去执行。 一旦改成了连接，就没有“内层、外层”的先后之分了，也就不存在“先执行子查询”这件事。

---

### 第二步：真正执行时，按「位置+类型」决定时机

保留下来的子查询，执行时机完全服从之前讲的 MySQL 执行顺序（`FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT`）：**子查询写在哪个子句里，就在哪个逻辑阶段执行**，不是所有子查询都挤在最开头执行。

#### 1. 非相关子查询（不依赖外层）：对应阶段开始时，一次性执行完

这类子查询因为和外层数据无关，优化器可以确定它只需要算一次。当执行流程走到它所在的子句阶段时，会**先把整个子查询执行完，拿到固定结果集，再继续该阶段的后续操作**。

举两个不同位置的例子：

- **写在 FROM 后**：在「数据源组装阶段」最先执行，生成临时派生表，再和其他表做连接。
    
    ```
    SELECT * 
    FROM (SELECT dept_id, AVG(sal) avg_sal FROM emp GROUP BY dept_id) t
    JOIN dept d ON t.dept_id = d.id;
    ```
    
    执行到 FROM 阶段时，先执行括号里的子查询得到 t 表，再做 JOIN。
    
- **写在 WHERE 后**：在「行级过滤阶段」开始时执行一次，得到结果列表，再用它去逐行过滤。
    
    ```
    SELECT * FROM emp 
    WHERE dept_id IN (SELECT id FROM dept WHERE name = '研发部');
    ```
    
    进入 WHERE 阶段后，先执行子查询拿到部门 id 列表，再用列表过滤 emp 表的行。
    

> 这类场景看起来像“先执行子查询”，但本质是**它刚好在当前阶段的开头执行**，而不是因为它叫“子查询”就拥有全 SQL 最高优先级。

#### 2. 相关子查询（依赖外层字段）：外层每遍历一行，才执行一次

这类子查询因为引用了外层的字段，**根本没办法提前单独执行**（单独跑会报“未知列”错误）。所以它的执行时机是： 外层查询遍历到某一行数据、需要用到子查询的结果来做判断时，才把当前行的字段值传进去，执行一次子查询，拿到结果后再判断外层这行是否保留。

最典型的就是 `EXISTS` 相关子查询：

```
SELECT * FROM emp e 
WHERE EXISTS (SELECT 1 FROM dept d WHERE d.id = e.dept_id);
```

执行流程是：

1. 开始遍历 emp 表，取出第一行员工数据；
2. 把这行的 `e.dept_id` 传入子查询，执行一次 EXISTS 判断；
3. 根据返回的 true/false，决定这行员工要不要保留；
4. 取下一行员工，重复步骤 2~3。

这种就是典型的**“遇到才执行”**，而且会反复执行很多次（外层有多少行，就可能执行多少次）。

---

### 最终总结

1. **不是“有子查询就先执行”**：优化器会优先尝试改写为连接，改不了才按子查询逻辑执行；
2. **不是统一时机执行**：子查询写在哪个子句（FROM/WHERE/SELECT/HAVING），就在对应的执行阶段执行，服从整体执行顺序；
3. **非相关子查询**：对应阶段开始时执行 1 次，结果复用；
4. **相关子查询**：外层每处理一行就执行 1 次，随用随算。


# 子查询位置  

子查询（嵌套的 SELECT 语句）几乎可以出现在 SQL 中所有需要「表/集合/单个值」的位置，按书写位置和作用分为**5 大类核心场景**，常用程度从高到低依次是：WHERE 子句 > FROM 子句 > SELECT 子句 > HAVING 子句 > DML（增删改）语句中。

下面结合你熟悉的学生-课程-成绩表结构，逐个讲解位置、作用、语法规则和示例。

---

### 一、WHERE 子句中（最常用，行级过滤）

#### 作用

把子查询的结果作为**过滤条件**，用来筛选外层表的行，是子查询最常见的用法。

#### 语法特点

- 子查询返回的结果用来和外层字段做匹配/比较
- 可以是**非相关子查询**（固定结果集），也可以是**相关子查询**（逐行校验）

#### 常见细分用法

1. **IN / NOT IN 集合匹配** 子查询返回单列多行结果，判断外层字段是否在集合中。

```
-- 查询选过001课程的学生
SELECT * FROM student
WHERE sid IN (SELECT sid FROM sc WHERE cid = '001');
```

2. **比较运算符（> < = >= <=）标量匹配** 子查询返回单行单列（单个值），和外层字段做大小比较。

```
-- 查询001课程中，成绩高于本课程平均分的学生
SELECT * FROM sc
WHERE cid = '001' 
  AND score > (SELECT AVG(score) FROM sc WHERE cid = '001');
```

3. **EXISTS / NOT EXISTS 存在性校验** 典型的相关子查询，只判断子查询是否能查到匹配的行。

```
-- 查询没学过叶平老师课的学生
SELECT s.sid, s.sname FROM student s
WHERE NOT EXISTS (
    SELECT 1 FROM sc
    JOIN course c ON sc.cid = c.cid
    JOIN teacher t ON c.tid = t.tid
    WHERE sc.sid = s.sid AND t.tname = '叶平'
);
```

---

### 二、FROM 子句中（第二常用，派生表）

#### 作用

把子查询的结果集**当作一张临时表**来使用，和普通物理表一样参与连接、分组等操作，也叫「派生表」「内联视图」。

#### 语法特点

- 必须给子查询结果起一个**表别名**，否则外层无法引用
- 几乎都是**非相关子查询**（独立执行，生成固定的临时表）
- 子查询内部可以是任意复杂的查询（分组、聚合、多表连接）

#### 示例

```
-- 查询平均成绩大于60的学生姓名和平均分
SELECT s.sname, t.avg_score
FROM student s
JOIN (
    -- 子查询：先算出每个学生的平均成绩，作为临时表 t
    SELECT sid, AVG(score) AS avg_score 
    FROM sc 
    GROUP BY sid
) t ON s.sid = t.sid
WHERE t.avg_score > 60;
```

> 执行时机：在 `FROM+JOIN` 数据源组装阶段最先执行，是所有子查询中执行最早的。

---

### 三、SELECT 子句中（标量子查询，逐行计算）

#### 作用

把子查询返回的单个值，作为**结果集中的一列**输出，相当于逐行关联计算一个额外字段。

#### 语法特点

- 必须是**标量子查询**：只能返回**单行单列**（一个值），返回多行多列会直接报错
- 通常是**相关子查询**：返回值随外层每一行的数据动态变化

#### 示例

```
-- 查询每个学生的学号、姓名、以及他的选课总数
SELECT 
  s.sid,
  s.sname,
  (SELECT COUNT(*) FROM sc WHERE sc.sid = s.sid) AS course_count
FROM student s;
```

> 执行时机：在 SELECT 字段投影阶段执行，外层每遍历一行，就执行一次子查询。

---

### 四、HAVING 子句中（分组后过滤）

#### 作用

把子查询的结果作为**分组后的过滤条件**，对 GROUP BY 分组聚合后的结果做二次筛选。

#### 语法特点

- 和 WHERE 用法类似，但作用于分组之后，因此可以配合聚合函数使用
- 可以是相关或非相关子查询

#### 示例

```
-- 查询平均成绩高于全年级总平均分的学生
SELECT sid, AVG(score) AS avg_score
FROM sc
GROUP BY sid
HAVING AVG(score) > (SELECT AVG(score) FROM sc);
```

---

### 五、DML 语句中（增删改操作里用）

子查询不仅能用在 SELECT 查询里，也能用在 INSERT、UPDATE、DELETE 的数据操作语句中，用来提供操作的数据范围。

#### 1. UPDATE 中

```
-- 把所有男生的001课程成绩都加5分
UPDATE sc 
SET score = score + 5
WHERE cid = '001' 
  AND sid IN (SELECT sid FROM student WHERE ssex = '男');
```

#### 2. DELETE 中

```
-- 删除叶平老师所教课程的所有成绩记录
DELETE FROM sc
WHERE cid IN (
    SELECT c.cid FROM course c
    JOIN teacher t ON c.tid = t.tid
    WHERE t.tname = '叶平'
);
```

#### 3. INSERT 中

```
-- 向成绩表插入：没上过003课的学生 + 002课程的平均分
INSERT INTO sc(sid, cid, score)
SELECT s.sid, '002', (SELECT AVG(score) FROM sc WHERE cid = '002')
FROM student s
WHERE s.sid NOT IN (SELECT sid FROM sc WHERE cid = '003');
```

---

### 补充：少见的位置

1. **ORDER BY / GROUP BY 子句**：语法支持但极少使用，通常用表达式或字段别名替代。
2. **JOIN 的 ON 关联条件中**：语法允许但可读性差，一般改写成普通表连接更清晰。

---

### 核心总结表

|放置位置|主要作用|常见子查询类型|执行时机|是否必须起别名|
|---|---|---|---|---|
|WHERE|行级数据过滤|相关/非相关|WHERE 过滤阶段|不需要|
|FROM|作为临时表参与关联|非相关|数据源组装阶段（最早）|必须|
|SELECT|输出额外计算列|相关（标量子查询）|SELECT 字段投影阶段|不需要|
|HAVING|分组后聚合过滤|相关/非相关|HAVING 分组后过滤阶段|不需要|
|DML 语句|提供增删改的数据范围|非相关|数据操作阶段|不需要|
